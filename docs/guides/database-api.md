# Build a database-backed JSON API

You want a JSON API whose data lives in PostgreSQL: create, read, update and delete users, with SQL you can read, queries the compiler checks, and migrations you can replay on any machine. You also want the failures to be clean: a `404` for a user that doesn't exist, a `400` for a body that isn't a user, and a health check that tells a load balancer when the database is gone. This guide builds `examples/database` from the dependencies to the running server, and every output is what that server answers.

## What you'll build

- A PostgreSQL database in Docker, with its schema made by a migration.
- Typed Gleam functions for each SQL query, generated by `dream_sql_generator`.
- A users API: `GET /users`, `GET /users/:id`, `POST /users`, `PUT /users/:id` and `DELETE /users/:id`.
- The real answers for a missing user, a wrong id and a body with a missing field, and a `/health` route.
- An operation that holds a workflow, and a test of it that needs no database.

## Which tool does what

| Tool | Its job | Where you see it |
|:---|:---|:---|
| `dream_postgres_client` | The PostgreSQL client and its connection pool | `database.gleam`, and every model |
| Cigogne | Runs the SQL migrations in `priv/migrations/` in order, once each | `make migrate` |
| `dream_sql_generator` | Reads each `.sql` file in `src/sql/`, asks the database for its types, and writes typed Gleam functions to `src/sql.gleam` | `make squirrel` |
| Services | Hand the pool to every controller | `services.gleam` |
| A model | Runs queries and turns rows into domain types | `models/user.gleam` |
| An operation | A workflow over more than one model | `operations/` |
| A view | Turns domain types into JSON | `views/user_view.gleam` |

#### The dev dependency <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/gleam.toml#L19-L23"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```toml
[tools.dream_sql_generator]
client_module = "dream_postgres_client"
```

- [`dream_postgres_client`](https://hex.pm/packages/dream_postgres_client) - The PostgreSQL client for Gleam, with its connection pool. It is a fork of `pog`, maintained for Dream.
- [`dream_sql_generator`](https://hex.pm/packages/dream_sql_generator) - Generates type-safe Gleam from SQL files. It is a fork of Squirrel, maintained for Dream. The `client_module` setting makes the generated code use `dream_postgres_client`.
- [`dream_postgres_driver`](https://hex.pm/packages/dream_postgres_driver) - The Erlang driver under `dream_postgres_client`. It is a fork of `pgo`, maintained for Dream. `dream_postgres_client` depends on it, so you do not add it yourself.
- `cigogne` - Database migrations

## Step 2: Start PostgreSQL with Docker Compose

Create `docker-compose.yml`. This is the file from `examples/database`:

#### docker-compose.yml <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/docker-compose.yml"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```yaml
version: "3.8"

services:
  postgres:
    image: postgres:16-alpine
    container_name: dream_example_database_postgres
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: dream_example_database_db
      PGDATA: /var/lib/postgresql/data/pgdata
    ports:
      - "5435:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres_data:
    driver: local
```

The database listens on port 5435 on your machine, so it does not collide with another PostgreSQL on port 5432.

### Shortcuts in a Makefile

Create `Makefile`. These are the targets of the Makefile of
`examples/database`. Its `test-integration` target, which runs the
integration tests of the example, is left out here. The example has no
unit tests, so `make test` runs `test-integration`. In your app, `test`
can run `gleam test` in its place. In CI the database
runs as a service of the job, so `make db-up` only starts it on your
machine:

#### The top of the Makefile <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/Makefile#L1-L10"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```makefile
# Docker Compose database connection URL
DATABASE_URL = postgres://postgres:postgres@localhost:5435/dream_example_database_db

.PHONY: run test test-integration clean db-up db-down db-logs db-shell db-reset migrate migrate-up migrate-down migrate-new squirrel

run:
	@gleam run -m main

test:
	@make test-integration
```

#### The database targets <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/Makefile#L71-L113"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```makefile

# Docker Compose commands for PostgreSQL
# In CI, PostgreSQL is a service of the job, on the same port.
db-up:
	@if [ -n "$$CI" ]; then \
		echo "PostgreSQL runs as a service of the CI job"; \
	else \
		docker-compose up -d postgres; \
		echo "Waiting for PostgreSQL to be ready..."; \
		timeout 30 bash -c 'until docker-compose exec -T postgres pg_isready -U postgres; do sleep 1; done' || true; \
	fi

db-down:
	@docker-compose down

db-logs:
	@docker-compose logs -f postgres

db-shell:
	@docker-compose exec postgres psql -U postgres -d dream_example_database_db

db-reset:
	@docker-compose down -v
	@docker-compose up -d postgres
	@echo "Waiting for PostgreSQL to be ready..."
	@timeout 30 bash -c 'until docker-compose exec -T postgres pg_isready -U postgres; do sleep 1; done' || true

# Migration commands using cigogne
migrate:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne all

migrate-up:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne up

migrate-down:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne down

migrate-new:
	@gleam run -m cigogne new --name $(name)

# Generate src/sql.gleam from the queries in src/sql/ with dream_sql_generator
squirrel:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m dream_sql_generator
```

**Why a Makefile?** Instead of remembering `gleam run -m dream_sql_generator`,
`gleam run -m cigogne all`, `docker-compose up`, etc., you just run
`make db-up`, `make migrate`, `make squirrel`. One command, no
thinking.

If you are new to Makefiles, you can think of each name (`run`,
`db-up`, `migrate`) as a **shortcut** for a longer command. You do not
need to know all of Make, you just need to know which shortcut to call
for common tasks.

```sql
  id SERIAL PRIMARY KEY,
```

## Step 5: Put the connection pool in services

Services hold the things that every request shares, such as the
database connection pool. The app in `examples/database` puts the pool
in three small files.

First, create `src/database.gleam`. It starts the connection pool:

### Starting the connection pool <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/database.gleam#L7-L37"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
import dream_postgres_client
import gleam/erlang/process
import gleam/option
import gleam/otp/actor

pub type DatabaseService {
  DatabaseService(connection: dream_postgres_client.Connection)
}

pub fn init_database() -> Result(DatabaseService, String) {
  // Create connection pool name
  let pool_name = process.new_name("dream_postgres_pool")

  // Configure PostgreSQL connection
  let config =
    dream_postgres_client.default_config(pool_name: pool_name)
    |> dream_postgres_client.host("localhost")
    |> dream_postgres_client.port(5435)
    |> dream_postgres_client.database("dream_example_database_db")
    |> dream_postgres_client.user("postgres")
    |> dream_postgres_client.password(option.Some("postgres"))
    |> dream_postgres_client.pool_size(10)

  // Start the connection pool
  case dream_postgres_client.start(config) {
    Ok(actor.Started(_pid, connection)) -> {
      Ok(DatabaseService(connection: connection))
    }
    Error(_) -> Error("Failed to start PostgreSQL connection pool")
  }
}
```

Then create `src/services.gleam`. It holds the database service:

### Services with a database service <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/services.gleam#L5-L17"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
import database.{type DatabaseService}

/// Application services
pub type Services {
  Services(database: DatabaseService)
}

/// Initialize all services
/// Uses assert to panic if initialization fails - adjust for production use
pub fn initialize_services() -> Services {
  let assert Ok(database_service) = database.init_database()
  Services(database: database_service)
}
```

Last, create `src/context.gleam`. Context holds per-request data.
This app keeps only a request ID in it:

### A small context type <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/context.gleam#L5-L12"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Database context for tracking per-request state
pub type DatabaseContext {
  DatabaseContext(request_id: String)
}

/// Template context with empty request_id
/// The request_id will be updated for each request
pub const context = DatabaseContext(request_id: "")
```

**What's happening here:**

1. `init_database()` builds a configuration for `dream_postgres_client`
   (the PostgreSQL client) and starts a connection pool. Starting the pool can fail, so
   `init_database()` returns a `Result`.
2. `initialize_services()` runs once when the server starts. If the
   database is not available, `let assert` stops the app at startup.
   Change this for production use.
3. Every controller gets `services` as an argument, and reads the pool
   from `services.database.connection`.
4. `DatabaseContext` is a custom context with one field. [Route requests and add middleware](https://github.com/TrustBound/dream/blob/main/docs/guides/routing.md)
   explains custom context in full.

**Why Services?**

A server with no database uses `EmptyServices`. This one has to give the database connection to its controllers.

Without Services, you'd need:
- Global variables (can't do safely in Gleam)
- Process dictionary (Erlang hack, not type-safe)
- Threading `db` through manually (tedious, error-prone)

Services solves this with type safety. The compiler verifies every controller gets the connection it needs.

## Step 7: Write the model

Create `src/models/user.gleam`. The model has one function for each
database action:

### The user model <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/models/user.gleam#L6-L75"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
import dream/http/error.{type Error, InternalServerError, NotFound}
import dream_postgres_client
import gleam/dynamic/decode
import gleam/list
import gleam/option
import gleam/time/timestamp
import sql
import types/user.{type User, User}

/// List all users
pub fn list(db: dream_postgres_client.Connection) -> Result(List(User), Error) {
  case sql.list_users(db) {
    Ok(returned) -> Ok(extract_all_users(returned))
    Error(_) -> Error(InternalServerError("Database error"))
  }
}

/// Get a single user by ID
pub fn get(
  db: dream_postgres_client.Connection,
  id: Int,
) -> Result(User, Error) {
  case sql.get_user(db, id) {
    Ok(returned) -> extract_first_user(returned)
    Error(_) -> Error(InternalServerError("Database error"))
  }
}

/// Create a new user
pub fn create(
  db: dream_postgres_client.Connection,
  name: String,
  email: String,
) -> Result(User, Error) {
  case sql.create_user(db, name, email) {
    Ok(returned) -> extract_created_user(returned)
    Error(_) -> Error(InternalServerError("Database error"))
  }
}

/// Update a user
pub fn update(
  db: dream_postgres_client.Connection,
  id: Int,
  name: String,
  email: String,
) -> Result(User, Error) {
  case sql.update_user(db, name, email, id) {
    Ok(returned) -> extract_updated_user(returned)
    Error(_) -> Error(InternalServerError("Database error"))
  }
}

/// Delete a user
pub fn delete(
  db: dream_postgres_client.Connection,
  id: Int,
) -> Result(Nil, Error) {
  case sql.delete_user(db, id) {
    Ok(_) -> Ok(Nil)
    Error(_) -> Error(InternalServerError("Database error"))
  }
}

/// Decoder for user create/update requests
pub fn decoder() -> decode.Decoder(#(String, String)) {
  use name <- decode.field("name", decode.string)
  use email <- decode.field("email", decode.string)
  decode.success(#(name, email))
}
```

`dream_sql_generator` makes one row type for each query, for example
`sql.GetUserRow` and `sql.ListUsersRow`. Thus the model has one small
function for each row type that converts the row to a `User`:

### Converting rows to users <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/models/user.gleam#L115-L131"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
fn row_to_user(row: sql.GetUserRow) -> User {
  User(
    id: row.id,
    name: row.name,
    email: row.email,
    created_at: option.unwrap(row.created_at, timestamp.system_time()),
  )
}

fn row_to_user_list(row: sql.ListUsersRow) -> User {
  User(
    id: row.id,
    name: row.name,
    email: row.email,
    created_at: option.unwrap(row.created_at, timestamp.system_time()),
  )
}
```

The other helpers in the file (`extract_first_user`,
`extract_all_users`, `extract_created_user`, `extract_updated_user`,
`row_to_user_create` and `row_to_user_update`) follow the same form.
See the [full model](https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/models/user.gleam).

**What's happening here:**

1. Models handle data access: getting data from the database.
2. They take `db: Connection` explicitly (no globals).
3. They return domain types (`User`), not database row structs.
4. They convert from DB rows to domain types inside helper functions
   like `row_to_user`.

If you are new to Gleam’s `Result` and pattern matching: each `case` on
`sql.*` checks whether the query succeeded (`Ok`) or failed (`Error`)
and then wraps database errors in the unified `dream.Error` type.

**Why a separate model?**

Models are the **write path** - handling incoming data and persistence:
- Accept what data we need (`decoder()`)
- Validate and store it (`create()`)
- Retrieve it (`get()`, `list()`)
- Convert DB rows → domain types

This keeps database concerns in one place.

```gleam
  |> json.to_string()

  |> json.to_string()
}
```

**What's happening here:**

Views handle presentation: formatting data for output as JSON strings.
They know **nothing** about how data is stored.

**Why separate from models?**

Views are the **read path** - formatting domain types for responses:
- Take domain types (`User`)
- Return formatted output (`String`)
- No database knowledge
- No error handling (that's the controller's job)

This separation means:
- Change database schema → update models only
- Add new output format (HTML, CSV) → update views only
- Controllers just orchestrate: model → view → response

```gleam
import models/user

/// List all users

/// Create a new user
pub fn create(
  request: Request,
  _context: DatabaseContext,
  services: Services,
) -> Response {
  let result = {
    use #(name, email) <- result.try(require_json(request, user.decoder()))
    let db = services.database.connection
    user_operations.create_user(db, name, email)
  }
```

The full file also has `update` and `delete` actions, which use the
same form.

The controller uses `utilities/response_helpers.gleam`, which maps a
`dream.Error` to a response. Copy it, and the `views/errors.gleam`
that it uses, from
[examples/database](https://github.com/TrustBound/dream/tree/3.0.0/examples/database/src).

**What's happening here:**

Controllers orchestrate the flow:

1. Extract and validate path parameters using `require_int` (returns a
   `Result` instead of panicking).
2. Decode the JSON body with `require_json(request, user.decoder())`.
   It reads the body as text, parses the JSON, and runs the decoder.
   If the body is not text, not JSON, or not valid user data, it
   returns `BadRequest` with the reason.
3. Call operations for data access (they return
   `Result(_, dream.Error)`).
4. Handle errors uniformly through `response_helpers.handle_error`
   (maps `dream.Error` to HTTP responses).
5. Call views for formatting, and build the response.

If you are new to the `use <- result.try(...)` pattern: it is Gleam’s
way of saying “if this step fails, stop here and return the error,
otherwise carry on”, without deeply nested `case` expressions.

**Why this pattern?**

- **`require_int`**: Safely extracts and validates path parameters. Returns `BadRequest` if missing or invalid, eliminating the need for `let assert`.
- **Flat `use` chains**: The `use` syntax keeps code readable without nested `case` statements.
- **Unified errors**: All errors use `dream.Error`, so controllers don't need to map between different error types.
- **Centralized error handling**: `response_helpers.handle_error` ensures consistent error responses across the application.

**The require_* pattern (recommended):**

#### Reading a path parameter <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/learn_building_api_show_user.gleam#L14"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
    use id <- result.try(require_int(request, "id"))
```

This pattern:
- Safely extracts and validates path parameters
- Returns `Result` types for error handling
- Works with flat `use` chains to keep code readable
- Handles missing or invalid parameters gracefully

**Note:** While `let assert` is still valid for path parameters (since the router guarantees they exist), `require_*` functions are preferred as they provide better error messages and work consistently with the unified error handling pattern.

**No nested cases:** Each controller uses flat `use` chains and extracts helpers to keep the code readable.

## Step 13: Move a workflow into an operation

The users API needs no operations: each action is one model call. An operation earns its place when an action is a workflow. This step uses the real code of the [tasks example](https://github.com/TrustBound/dream/tree/3.0.0/examples/tasks).

### The Problem

The tasks example lets you type a new tag name on a task. To save it, the app must:

1. Find the tag with that name, or create it
2. Attach the tag to the task
3. Get all tags, so the page can show the updated tag selector

Each step is simple. Together they are a small workflow. If the controller does all of it, the controller mixes HTTP work with business rules.

### When to Use Operations

**Keep it in the controller:**

The project list in

```gleam
/// Create a new tag and attach it to a task
///
/// Returns the newly created tag or an error.
pub fn create_and_attach(
  db: Connection,
  task_id: Int,
  tag_name: String,
) -> Result(Tag, Error) {
  let data = TagData(name: tag_name, color: option.None)

  use tag <- result.try(tag_model.get_or_create(db, data))
  use _ <- result.try(tag_model.add_to_task(db, task_id, tag.id))

  Ok(tag)
}
```

**What's happening:**

1. `tag_model.get_or_create` finds the tag with that name, or creates it.
2. `tag_model.add_to_task` attaches the tag to the task.
3. If a step fails, `result.try` stops and returns the error.

The operation knows nothing about HTTP. It takes a database connection and plain values, and it returns `Result(Tag, Error)`.

### Call it from the controller

The controller in `src/controllers/tags_controller.gleam` calls the operation:

#### The controller calls the operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/controllers/tags_controller.gleam#L60-L89"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Create tag and add to task (returns updated tag selector HTML)
pub fn create_and_add_to_task(
  request: http.Request,
  _context: TasksContext,
  services: Services,
) -> http.Response {
  let result = {
    use task_id <- result.try(http.require_int(request, "task_id"))
    use form <- result.try(http.require_form(request))
    use tag_name <- result.try(http.require_field(form, "tag_name"))

    use _ <- result.try(tag_operations.create_and_attach(
      services.db,
      task_id,
      tag_name,
    ))

    use all_tags <- result.try(tag_operations.list_all(services.db))
    Ok(#(all_tags, task_id))
  }

  case result {
    Ok(#(all_tags, task_id)) ->
      http.html_response(
        http.ok,
        tag_components.tag_selector_html(all_tags, task_id),
      )
    Error(err) -> response_helpers.handle_error(err)
  }
}
```

The controller is thin:

- It reads the task ID and the tag name with `require_int`, `require_form` and `require_field`. Each one returns a `Result`. For a form field that can be missing, use `field_optional`, which returns an `Option`.
- It calls the operation, which returns `dream.Error` on failure.
- It sends every error to `response_helpers.handle_error`.
- It builds the response.

The workflow lives in the operation. The controller and the operation use the same error type (`dream.Error`), so the controller does not map errors.

### When You Need Operations

**Use operations when:**
- An action uses 2 or more models
- An action has more than one step that must happen in order
- A business rule spans more than one entity
- More than one controller needs the same workflow

**Don't use operations when:**
- The action is simple CRUD (one model, one action)
- There are no business rules
- Nothing needs coordination

**Most controllers don't need operations.** Extract one only when a controller does too much.

### An operation over services

An Operation is just a **function**. Typically it:

- Takes `Services` and the input it needs (IDs, payloads, etc.).
- Calls models and other services.
- Returns a `Result(success_value, Error)`, with `Error` from
  `dream/http/error`, so controllers can handle errors uniformly.

**Example: Reordering Tasks**

This operation moves a task to a new position and shifts the other tasks. An unknown task gives `NotFound`, and a position outside the list gives `BadRequest`.

#### The reorder_task operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_tasks.gleam#L23-L40"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn reorder_task(
  services: Services,
  task_id: Int,
  new_position: Int,
) -> Result(List(Task), Error) {
  // In a real app, this might also:
  // 1. Check permissions
  // 2. Save the new order in the database
  // 3. Log the activity
  // 4. Broadcast an event via WebSocket
  use task <- result.try(find_task(services.tasks, task_id))
  use Nil <- result.try(check_position(services.tasks, new_position))
  let other_tasks =
    list.filter(services.tasks, fn(other) { other.id != task_id })
  // Shift the other tasks to make room
  let #(before, after) = list.split(other_tasks, new_position - 1)
  Ok(list.flatten([before, [task], after]))
}
```

### Using in a Controller

The controller becomes a simple coordinator:

#### The reorder controller <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_tasks.gleam#L42-L58"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn reorder(
  request: Request,
  _context: EmptyContext,
  services: Services,
) -> Response {
  let result = {
    use id <- result.try(require_int(request, "id"))
    use form <- result.try(require_form(request))
    use new_position <- result.try(require_field_int(form, "position"))
    reorder_task(services, id, new_position)
  }

  case result {
    Ok(tasks) -> json_response(ok, task_ids_to_json(tasks))
    Error(failure) -> respond_with_error(failure)
  }
}
```

This controller uses `require_int` to safely extract the path parameter
and `require_field_int` to read `position` from the form body, then
calls the operation. The `use` syntax keeps the code flat and
readable.

All errors from the parameters and from the operation (which returns
`Result(_, Error)`) flow into the final `case result`.
`respond_with_error` turns each one into an HTTP response with
`error.to_status_code` and `error.message`.

The important shift is:

- Before: controller both **decides** what to do and **does** it.
- After: controller **decides** what to do, Operation **does** it.

### Benefits

1.  **Testability:** You can unit test the operation without mocking HTTP requests.
2.  **Reusability:** Call the same operation from a REST API, a GraphQL resolver, or a background job.
3.  **Clarity:** The controller reads like a summary of what's happening, not the implementation details.

### Advanced: Service Coordination

Operations are the perfect place to coordinate multiple services.

#### The publish_post operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_posts.gleam#L21-L31"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn publish_post(services: Services, post_id: Int) -> Result(Post, Error) {
  use post <- result.try(find_post(services.posts, post_id))
  let published_post = Post(..post, published: True)

  // Side effects coordinated here. A failure stops the chain and comes
  // back to the controller as an Error.
  use Nil <- result.try(services.add_to_search_index(published_post))
  use Nil <- result.try(services.notify_subscribers(published_post))

  Ok(published_post)
}
```

Use the `use` syntax (Gleam's equivalent of `do` notation) to chain operations flatly, avoiding nested cases.

Do not discard the result of a side effect with `let _ =`. If the search index or the mailer fails, nobody then sees the error. In the example, each side effect returns a `Result`, and a failure comes back to the controller.

**Important:** Operations should return `Result(_, Error)` to keep error handling consistent across the application. This allows controllers to handle all errors uniformly without needing to map between different error types.

## Models with the dream_postgres helpers

Models handle data access. They are functions that:
1.  Take a database connection.
2.  Execute SQL queries (using `dream_postgres` and `dream_sql_generator`).
3.  Convert database rows to domain types.
4.  Return a `Result`.

These examples come from the project model in the tasks example. `dream_sql_generator` generates the `models/project/sql` module, and `dream_postgres/query` gives the `first_row()` and `all_rows()` helpers.

#### Getting a Single Record <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/project_model.gleam#L14-L21"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Get a single project by ID
pub fn get(db: Connection, project_id: Int) -> Result(Project, Error) {
  case sql.get_project(db, project_id) |> query.first_row() {
    Ok(row) -> Ok(row_to_project(row))
    Error(query.NotFound) -> Error(NotFound("Project not found"))
    Error(query.DatabaseError) -> Error(InternalServerError("Database error"))
  }
}
```

`query.first_row()` returns `query.NotFound` when the query gives no rows. The model maps it to a 404 error.

#### Listing Multiple Records <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/project_model.gleam#L23-L29"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// List all projects
pub fn list(db: Connection) -> Result(List(Project), Error) {
  case sql.list_projects(db) |> query.all_rows() {
    Ok(rows) -> Ok(list.map(rows, list_row_to_project))
    Error(_) -> Error(InternalServerError("Database error"))
  }
}
```

#### Creating a Record <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/project_model.gleam#L31-L43"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Create a new project
pub fn create(db: Connection, data: ProjectData) -> Result(Project, Error) {
  let description = option.unwrap(data.description, "")
  let color = option.unwrap(data.color, "")

  case
    sql.create_project(db, data.name, description, color)
    |> query.first_row()
  {
    Ok(row) -> Ok(create_row_to_project(row))
    Error(_) -> Error(InternalServerError("Database error"))
  }
}
```

The controller decodes the request body into a `ProjectData` record. The model gives defaults to the optional fields and runs the insert.

#### Converting a Row <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/project_model.gleam#L53-L62"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
// Convert Squirrel row to domain type
fn row_to_project(row: sql.GetProjectRow) -> Project {
  Project(
    id: row.id,
    name: row.name,
    description: row.description,
    color: row.color,
    created_at: timestamp_to_string(row.created_at),
  )
}
```

Each query has its own row type, so the model has one small function for each row type. The controller gets a `Project` and never sees a row.

### Best Practices
- **Return Domain Types:** Don't leak SQL row types to the controller. Convert them in the model.
- **Explicit Connection:** Pass `db: Connection` explicitly.
- **Type-Safe SQL:** Use `dream_sql_generator` to generate type-safe SQL functions.
- **Unified Errors:** Return `Result(_, dream.Error)` to keep error handling consistent across the application.
- **Use Query Helpers:** `dream_postgres/query` provides `first_row()` and `all_rows()` helpers that handle common query result patterns.

## Test your code

An operation that takes its data from services can be tested with no database: build the services in the test. This test checks the `reorder_task` operation above, the happy path and both errors:

### Test an operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/guide_database_api_test.gleam"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
//// Database API guide: a test of an operation, with no database
////
//// The operation is reorder_task of test/snippets/operations_guide_tasks.gleam.
//// Its tasks come from Services, so the test builds the services it needs.

import dream/http/error.{BadRequest, NotFound}
import dream_test/matchers.{be_equal, or_fail_with, should}
import dream_test/suite.{type TestSuite}
import dream_test/unit.{describe, it}
import snippets/operations_guide_tasks.{Services, Task}

fn three_tasks() -> operations_guide_tasks.Services {
  Services(tasks: [
    Task(id: 1, title: "Write"),
    Task(id: 2, title: "Test"),
    Task(id: 3, title: "Ship"),
  ])
}

pub fn tests() -> TestSuite {
  describe("reorder_task", [
    it("moves task 3 to the first place", fn() {
      // Arrange
      let services = three_tasks()

      // Act
      let reordered = operations_guide_tasks.reorder_task(services, 3, 1)

      // Assert
      reordered
      |> should
      |> be_equal(
        Ok([
          Task(id: 3, title: "Ship"),
          Task(id: 1, title: "Write"),
          Task(id: 2, title: "Test"),
        ]),
      )
      |> or_fail_with("task 3 should come first")
    }),
    it("keeps every task when it moves one", fn() {
      // Arrange
      let services = three_tasks()

      // Act
      let reordered = operations_guide_tasks.reorder_task(services, 1, 3)

      // Assert
      reordered
      |> should
      |> be_equal(
        Ok([
          Task(id: 2, title: "Test"),
          Task(id: 3, title: "Ship"),
          Task(id: 1, title: "Write"),
        ]),
      )
      |> or_fail_with("task 1 should come last, and no task should be lost")
    }),
    it("gives NotFound for an unknown task", fn() {
      // Arrange
      let services = three_tasks()

      // Act
      let reordered = operations_guide_tasks.reorder_task(services, 9, 1)

      // Assert
      reordered
      |> should
      |> be_equal(Error(NotFound("Task not found")))
      |> or_fail_with("task 9 should not be found")
    }),
    it("gives BadRequest for a position past the end", fn() {
      // Arrange
      let services = three_tasks()

      // Act
      let reordered = operations_guide_tasks.reorder_task(services, 1, 4)

      // Assert
      reordered
      |> should
      |> be_equal(
        Error(BadRequest("Position must be between 1 and the task count")),
      )
      |> or_fail_with("position 4 of 3 tasks should be refused")
    }),
  ])
}
```

## Common pitfalls

- **`src/sql.gleam` is out of date.** `dream_sql_generator` generates it from the `.sql` files and the live schema. After you change a query or a migration, run `make migrate` and then `make squirrel`. The example's integration run fails when the file isn't what `dream_sql_generator` generates.
- **The app stops at start with a database error.** `initialize_services` uses `let assert` on the pool, so a database that isn't up stops the app at once. That's on purpose for the example. In production, start the pool in a supervisor or retry, and keep the health check.
- **Row types in controllers.** `dream_sql_generator` makes one row type per query. Convert rows to your domain type in the model, so a new column doesn't ripple through every controller.
- **A side effect's result thrown away.** `let _ = search.index(post)` hides a failure. Return a `Result` from every step of an operation and chain them with `use`.
- **Port 5432 is taken.** The example maps PostgreSQL to port 5435 on your machine, so it doesn't collide with a local PostgreSQL.
