# Build a database-backed JSON API

You want a JSON API whose data lives in PostgreSQL: create, read, update and delete users, with SQL you can read, queries the compiler checks, and migrations you can replay on any machine. You also want the failures to be clean: a `404` for a user that doesn't exist, a `400` for a body that isn't a user, and a health check that tells a load balancer when the database is gone. This guide builds `examples/database` from the dependencies to the running server, and every output is what that server answers.

## What you'll build

- A PostgreSQL database in Docker, with its schema made by a migration.
- A typed model module for each table, generated by `dream_model` from one `.sql` file for each query.
- A users API: `GET /users`, `GET /users/:id`, `POST /users`, `PUT /users/:id` and `DELETE /users/:id`.
- The real answers for a missing user, a wrong id and a body with a missing field, and a `/health` route.
- An operation that holds a workflow, and a test of it that needs no database.

## Which tool does what

| Tool | Its job | Where you see it |
|:---|:---|:---|
| `dream_postgres_client` | The PostgreSQL client and its connection pool | `database.gleam`, and every model |
| Cigogne | Runs the SQL migrations in `priv/migrations/` in order, once each | `make migrate` |
| `dream_model` | Reads the `.sql` files of each folder in `src/models/`, asks the database for their types, and writes one model module for each folder, such as `src/models/user.gleam` | `make models` |
| Services | Hand the pool to every controller | `services.gleam` |
| A model | Runs queries and returns domain types and data errors. dream_model generates it | `models/user.gleam` |
| An operation | A workflow over more than one model | `operations/` |
| A view | Turns domain types into JSON | `views/user_view.gleam` |

#### The database targets <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/Makefile#L74-L116"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```makefile

# Docker Compose commands for PostgreSQL
# In CI, PostgreSQL is a service of the job, on the same port.
db-up:
	@if [ -n "$$CI" ]; then \
		echo "PostgreSQL runs as a service of the CI job"; \
	else \
		docker-compose up -d postgres; \
		echo "Waiting for PostgreSQL to be ready..."; \
		timeout 30 bash -c 'until docker-compose exec -T postgres pg_isready -U postgres; do sleep 1; done' || true; \
	fi

db-down:
	@docker-compose down

db-logs:
	@docker-compose logs -f postgres

db-shell:
	@docker-compose exec postgres psql -U postgres -d dream_example_database_db

db-reset:
	@docker-compose down -v
	@docker-compose up -d postgres
	@echo "Waiting for PostgreSQL to be ready..."
	@timeout 30 bash -c 'until docker-compose exec -T postgres pg_isready -U postgres; do sleep 1; done' || true

# Migration commands using cigogne
migrate:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne all

migrate-up:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne up

migrate-down:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m cigogne down

migrate-new:
	@gleam run -m cigogne new --name $(name)

# Generate the model modules from the queries in src/models/ with dream_model
models:
	@export DATABASE_URL="$(DATABASE_URL)" && gleam run -m dream_model
```

**Why a Makefile?** Instead of remembering `gleam run -m dream_model`,
`gleam run -m cigogne all`, `docker-compose up`, etc., you just run
`make db-up`, `make migrate`, `make models`. One command, no
thinking.

If you are new to Makefiles, you can think of each name (`run`,
`db-up`, `migrate`) as a **shortcut** for a longer command. You do not
need to know all of Make, you just need to know which shortcut to call
for common tasks.


The hints say what each function returns and which errors it gives:

- `-- returns: one User` returns one `User`. With no row, the function
  returns `dream_errors.NotFound`.
- `-- returns: many User` returns a `List(User)`.
- `-- unique: users_email_key` turns a violation of that unique
  constraint into `dream_errors.Conflict`, with the database error as
  its cause.
- A timeout gives `dream_errors.Timeout`, no free connection gives
  `dream_errors.Unavailable`, and every other database error gives
  `dream_errors.Failed`. Each one has a message for developers and the
  original error as its cause.

A hint holds no text for the client. The operation gives each error its
text, in [Step 7](#step-7-call-the-model-from-an-operation).

The example also has `update.sql` and `delete.sql`, and the queries of
the post model in `src/models/post/`.

### Generate the model

#### Generate the code <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/test/integration/models.sh#L8"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>


This creates `src/models/user.gleam`. dream_model names each function
after its file: `create()`, `get()`, `list()`, `update()` and `delete()`.
All the queries of the folder return the same columns, so they share one
`User` record. A column that can be NULL, such as `created_at`, is an
`Option`.

**Why dream_model?** Instead of writing raw SQL strings and parsing
results manually, dream_model asks the database for the type of each
column and parameter, and generates Gleam functions with those types.
The compiler then catches a wrong type at compile time. Do not edit the
generated module. Change a `.sql` file and run `make models` again. In
CI, `gleam run -m dream_model -- --check` fails when a generated module
is out of date.

## Step 5: Put the connection pool in services

Services hold the things that every request shares, such as the
database connection pool. The app in `examples/database` puts the pool
in three small files.

First, create `src/database.gleam`. It starts the connection pool, then
checks that the schema is still the one that dream_model generated the
models from:

### Starting the connection pool <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/database.gleam#L12-L113"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
}
import dream_postgres_client.{type Connection, ConnectionUnavailable, start}
import gleam/erlang/process.{sleep}
import gleam/int.{to_string}
import gleam/io.{println_error}
import gleam/option
import gleam/otp/actor.{Started}
import gleam/result
import models/post.{schema_fingerprint}
import models/user

pub type DatabaseService {
  DatabaseService(connection: dream_postgres_client.Connection)
}

pub fn init_database() -> Result(DatabaseService, String) {
  // Create connection pool name
  let pool_name = process.new_name("dream_postgres_pool")

  // Configure PostgreSQL connection
  let config =
    dream_postgres_client.default_config(pool_name: pool_name)
    |> dream_postgres_client.host("localhost")
    |> dream_postgres_client.port(5435)
    |> dream_postgres_client.database("dream_example_database_db")
    |> dream_postgres_client.user("postgres")
    |> dream_postgres_client.password(option.Some("postgres"))
    |> dream_postgres_client.pool_size(10)

  // Start the connection pool
  use connection <- result.try(case start(config) {
    Ok(Started(_pid, connection)) -> Ok(connection)
    Error(_) -> Error("Failed to start PostgreSQL connection pool")
  })

  // Wait for the database, then stop with a clear message when the schema
  // changed after dream_model generated the models
  use Nil <- result.try(
    check_schema_waiting_for_database(connection, [
      user.schema_fingerprint,
      schema_fingerprint,
    ])
    |> result.map_error(format_schema_check_error),
  )
  Ok(DatabaseService(connection: connection))
}

/// How long the app runs the schema check again while the database cannot
/// be reached, in milliseconds. The last check can start just before this
/// deadline, and a failed check takes 2 to 3 seconds, the time that the
/// pool waits for a connection.
const schema_check_deadline_ms = 30_000

/// The time between two schema checks, in milliseconds
const schema_check_delay_ms = 2000

/// Runs `client.check_schema`, and waits for a database that cannot be
/// reached yet. When the pool has no connection, it prints one line, waits
/// `schema_check_delay_ms` and runs the check again, until
/// `schema_check_deadline_ms` passed since the first check. A changed
/// schema and the other database errors give the error at once.
pub fn check_schema_waiting_for_database(
  connection: Connection,
  expected: List(SchemaFingerprint),
) -> Result(Nil, SchemaCheckError) {
  check_schema_until(connection, expected, monotonic_time(Millisecond))
}

fn check_schema_until(
  connection: Connection,
  expected: List(SchemaFingerprint),
  started_ms: Int,
) -> Result(Nil, SchemaCheckError) {
  let result = check_schema(connection, expected)
  let elapsed_ms = monotonic_time(Millisecond) - started_ms
  case result {
    Error(SchemaUnreadable(error: ConnectionUnavailable, ..) as error)
      if elapsed_ms + schema_check_delay_ms < schema_check_deadline_ms
    -> {
      println_error(
        "Waiting for the database ("
        <> to_string(elapsed_ms / 1000)
        <> "s of "
        <> to_string(schema_check_deadline_ms / 1000)
        <> "s): "
        <> format_schema_check_error(error),
      )
      sleep(schema_check_delay_ms)
      check_schema_until(connection, expected, started_ms)
    }
    _ -> result
  }
}

/// The unit of `monotonic_time`. Erlang reads it as the atom `millisecond`.
type TimeUnit {
  Millisecond
}

/// The time of a clock that never goes back, for durations
@external(erlang, "erlang", "monotonic_time")
fn monotonic_time(unit: TimeUnit) -> Int
```

Then create `src/services.gleam`. It holds the database service:

### Services with a database service <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/services.gleam#L5-L32"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
import database.{type DatabaseService}
import gleam/io.{println_error}

/// Application services
pub type Services {
  Services(database: DatabaseService)

/// Initialize all services
/// Stops the app with the error message if initialization fails, for
/// example when the database cannot be reached or the schema changed
/// after dream_model generated the models

  case database.init_database() {
    Ok(database_service) -> Services(database: database_service)
    Error(message) -> stop(message)
  }
```

Last, create `src/context.gleam`. Context holds per-request data.
This app keeps only a request ID in it:

### A small context type <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/context.gleam#L5-L12"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Database context for tracking per-request state
pub type DatabaseContext {
  DatabaseContext(request_id: String)
}

/// Template context with empty request_id
/// The request_id will be updated for each request
pub const context = DatabaseContext(request_id: "")
```

**What's happening here:**

1. `init_database()` builds a configuration for `dream_postgres_client`
   (the PostgreSQL client) and starts a connection pool. Starting the pool can fail, so
   `init_database()` returns a `Result`.
2. `client.check_schema` compares the `schema_fingerprint` of each
   generated model with the schema of the database. When a migration
   changed a table after the generation, it fails with a message that
   names the model and its tables. Run `make models` to fix it.
3. `check_schema_waiting_for_database` runs `client.check_schema`, and
   gives the database time to start. When the pool has no connection,
   `check_schema` gives `SchemaUnreadable` with
   `dream_postgres_client.ConnectionUnavailable`. The function then prints
   one line, such as `Waiting for the database (6s of 30s): ...`, waits
   2 seconds, and runs the check again, for at most 30 seconds. It reads
   the time from the monotonic clock of Erlang. A changed
   schema and the other database errors stop the app at once. The two
   constants `schema_check_deadline_ms` and `schema_check_delay_ms` set the
   deadline and the wait.
4. `initialize_services()` runs once when the server starts. If the
   database cannot be reached after the last attempt, or the schema
   changed, `stop` prints the message of
   `client.format_schema_check_error` and ends the app with exit status 1,
   with no crash report.
5. Every controller gets `services` as an argument, and reads the pool
   from `services.database.connection`.
6. `DatabaseContext` is a custom context with one field. [Route requests and add middleware](https://hexdocs.pm/dream/3.0.0/guides/routing.html)
   explains custom context in full.

**Why Services?**

A server with no database uses `EmptyServices`. This one has to give the database connection to its controllers.

Without Services, you'd need:
- Global variables (can't do safely in Gleam)
- Process dictionary (Erlang hack, not type-safe)
- Threading `db` through manually (tedious, error-prone)

Services solves this with type safety. The compiler verifies every controller gets the connection it needs.

## Step 6: Read the generated model

`make models` wrote `src/models/user.gleam`. Do not edit it. It holds:

- The `User` record: `id`, `name`, `email` and `created_at`. The
  `created_at` column has a default but no `NOT NULL`, so it is
  `Option(client.Timestamp)`.
- One function for each `.sql` file. Each one takes the connection
  first, then the parameters of the query, and returns
  `Result(_, dream_errors.Error(client.QueryError))`, the shared error
  of the Dream ecosystem. For example
  `get(db, id) -> Result(User, dream_errors.Error(client.QueryError))`
  and `create(db, name, email)` with the same error type.
- `schema_fingerprint`, the value that `check_schema` uses.

The functions already turn the database answers into data errors: no
row gives `NotFound`, a taken email gives `Conflict`, a timeout gives
`Timeout`, no connection gives `Unavailable`, and any other failure
gives `Failed`. Each message is for developers and logs.
The model has no HTTP status and no text for the client, and needs no
hand-written code.

## Step 7: Call the model from an operation

The controller in the next steps does not call the model directly. It
calls `src/operations/user_operations.gleam`. In this app, each
operation calls the generated model and maps its error to a Dream
error:

### The texts of the user errors <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/operations/user_operations.gleam#L55-L68"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// The Dream error of a model error. A missing row and a taken email keep
/// their own texts. Every other error goes through `error.from_shared`,
/// which never shows the developer message of the model error.
fn user_error(model_error: dream_errors.Error(QueryError)) -> Error {
  case model_error {
    dream_errors.NotFound(..) -> NotFound("User not found")
    dream_errors.Conflict(cause:, ..) ->
      case violated_constraint(cause) {
        Ok("users_email_key") -> Conflict("Email already taken")
        _ -> from_shared(model_error)
      }
    _ -> from_shared(model_error)
  }
}
```

A missing user and a taken email keep their own texts. The cause of a
`Conflict` is the database error, and `client.violated_constraint`
gives the name of its constraint. Every other error goes through
`error.from_shared`: a timeout gives `GatewayTimeout` (504), no free
connection gives `ServiceUnavailable` (503), and a failed query gives
`InternalServerError` (500). `from_shared` gives a fixed, generic text
and never the message of the model error. That message is for
developers and logs, because it can name tables, constraints and
values.

The controller then gets one error type, `dream.Error`, from the
operation and from `require_int` and `require_json`. An operation is the
place for business logic that uses more than one model. [Step 13](#step-13-move-a-workflow-into-an-operation)
explains when an operation earns its place.

**What's happening here:**

Views handle presentation: formatting data for output as JSON strings.
They know **nothing** about how data is stored.

**Why separate from models?**

Views are the **read path** - formatting domain types for responses:
- Take domain types (`User`)
- Return formatted output (`String`)
- No database knowledge
- No error handling (that's the controller's job)

This separation means:
- Change database schema → update models only
- Add new output format (HTML, CSV) → update views only
- Controllers just orchestrate: model → view → response

### The request decoder <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/database/src/controllers/users_controller.gleam#L107-L112"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
  use name <- field("name", string)
  use email <- field("email", string)
  success(#(name, email))
}
```

The controller uses `utilities/response_helpers.gleam`, which maps a
`dream.Error` to a response. Copy it, and the `views/errors.gleam`
that it uses, from
[examples/database](https://github.com/TrustBound/dream/tree/3.0.0/examples/database/src).

**What's happening here:**

Controllers orchestrate the flow:

1. Extract and validate path parameters using `require_int` (returns a
   `Result` instead of panicking).
2. Decode the JSON body with `require_json(request, user_decoder())`.
   It reads the body as text, parses the JSON, and runs the decoder.
   If the body is not text, not JSON, or not valid user data, it
   returns `BadRequest` with the reason.
3. Call operations for data access (they return
   `Result(_, dream.Error)`, mapped from the errors of the models).
4. Handle errors uniformly through `response_helpers.handle_error`
   (maps `dream.Error` to HTTP responses).
5. Call views for formatting, and build the response.

If you are new to the `use <- result.try(...)` pattern: it is Gleam’s
way of saying “if this step fails, stop here and return the error,
otherwise carry on”, without deeply nested `case` expressions.

**Why this pattern?**

- **`require_int`**: Safely extracts and validates path parameters. Returns `BadRequest` if missing or invalid, eliminating the need for `let assert`.
- **Flat `use` chains**: The `use` syntax keeps code readable without nested `case` statements.
- **Unified errors**: The operations map the data errors of the models to `dream.Error`, so controllers handle one error type.
- **Centralized error handling**: `response_helpers.handle_error` ensures consistent error responses across the application.

**The require_* pattern (recommended):**

#### Reading a path parameter <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/learn_building_api_show_user.gleam#L14"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
    use id <- result.try(require_int(request, "id"))
```

This pattern:
- Safely extracts and validates path parameters
- Returns `Result` types for error handling
- Works with flat `use` chains to keep code readable
- Handles missing or invalid parameters gracefully

**Note:** While `let assert` is still valid for path parameters (since the router guarantees they exist), `require_*` functions are preferred as they provide better error messages and work consistently with the unified error handling pattern.

**No nested cases:** Each controller uses flat `use` chains and extracts helpers to keep the code readable.

## Step 13: Move a workflow into an operation

The users API needs no operations: each action is one model call. An operation earns its place when an action is a workflow. This step uses the real code of the [tasks example](https://github.com/TrustBound/dream/tree/3.0.0/examples/tasks).

### The Problem

The tasks example lets you type a new tag name on a task. To save it, the app must:

1. Find the tag with that name, or create it
2. Attach the tag to the task
3. Get all tags, so the page can show the updated tag selector

Each step is simple. Together they are a small workflow. If the controller does all of it, the controller mixes HTTP work with business rules.

### When to Use Operations

**Keep it in the controller:**

The project list in
[examples/tasks](https://github.com/TrustBound/dream/tree/3.0.0/examples/tasks/src)
calls one model and formats the result. It needs no operation:

```gleam
  }

  case result {
    Ok(#(task, tags)) -> http.html_response(http.ok, task_view.card(task, tags))
    Error(err) -> response_helpers.handle_error(err)
  }
}
```

**The controller stays simple:** It reads the parameters, calls the operation and returns a response.

**The operation handles the logic:** The business rules live in one place.

### Write the operation

The tag workflow lives in `src/operations/tag_operations.gleam`:

#### Create and attach a tag <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/operations/tag_operations.gleam#L19-L37"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Create a new tag and attach it to a task
///
/// Returns the newly created tag or an error.
pub fn create_and_attach(
  db: Connection,
  task_id: Int,
  tag_name: String,
) -> Result(Tag, Error) {
  let data = TagData(name: tag_name, color: option.None)

  // A tag with no color stores an empty color.
  use created <- try(
    get_or_create(db, data.name, Some(unwrap(data.color, "")))
    |> map_error(tag_error),
  )
  use _ <- try(add_to_task(db, task_id, created.id) |> map_error(tag_error))

  Ok(created)
}
```

**What's happening:**

1. `tag.get_or_create` finds the tag with that name, or creates it. A
   tag with no color stores an empty color.
2. `tag.add_to_task` attaches the tag to the task. dream_model generated
   both functions from `src/models/tag/get_or_create.sql` and
   `src/models/tag/add_to_task.sql`.
3. If a step fails, `result.try` stops and returns the error.

The operation knows nothing about HTTP. It takes a database connection and plain values, and it returns `Result(Tag, Error)`.

### Call it from the controller

The controller in `src/controllers/tags_controller.gleam` calls the operation:

#### The controller calls the operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/controllers/tags_controller.gleam#L60-L89"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
/// Create tag and add to task (returns updated tag selector HTML)
pub fn create_and_add_to_task(
  request: http.Request,
  _context: TasksContext,
  services: Services,
) -> http.Response {
  let result = {
    use task_id <- result.try(http.require_int(request, "task_id"))
    use form <- result.try(http.require_form(request))
    use tag_name <- result.try(http.require_field(form, "tag_name"))

    use _ <- result.try(tag_operations.create_and_attach(
      services.db,
      task_id,
      tag_name,
    ))

    use all_tags <- result.try(tag_operations.list_all(services.db))
    Ok(#(all_tags, task_id))
  }

  case result {
    Ok(#(all_tags, task_id)) ->
      http.html_response(
        http.ok,
        tag_components.tag_selector_html(all_tags, task_id),
      )
    Error(err) -> response_helpers.handle_error(err)
  }
}
```

The controller is thin:

- It reads the task ID and the tag name with `require_int`, `require_form` and `require_field`. Each one returns a `Result`. For a form field that can be missing, use `field_optional`, which returns an `Option`.
- It calls the operation, which maps the errors of the models and returns `dream.Error` on failure.
- It sends every error to `response_helpers.handle_error`.
- It builds the response.

The workflow lives in the operation. The controller and the operation use the same error type (`dream.Error`), so the controller does not map errors.

### When You Need Operations

**Use operations when:**
- An action uses 2 or more models
- An action has more than one step that must happen in order
- A business rule spans more than one entity
- More than one controller needs the same workflow

**Don't use operations when:**
- The action is simple CRUD (one model, one action)
- There are no business rules
- Nothing needs coordination

**Most controllers don't need operations.** Extract one only when a controller does too much.

### Operations with services

### An operation over services

An Operation is just a **function**. Typically it:

- Takes `Services` and the input it needs (IDs, payloads, etc.).
- Calls models and other services.
- Returns a `Result(success_value, Error)`, with `Error` from
  `dream/http/error`, so controllers can handle errors uniformly.

**Example: Reordering Tasks**

This operation moves a task to a new position and shifts the other tasks. An unknown task gives `NotFound`, and a position outside the list gives `BadRequest`.

#### The reorder_task operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_tasks.gleam#L23-L40"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn reorder_task(
  services: Services,
  task_id: Int,
  new_position: Int,
) -> Result(List(Task), Error) {
  // In a real app, this might also:
  // 1. Check permissions
  // 2. Save the new order in the database
  // 3. Log the activity
  // 4. Broadcast an event via WebSocket
  use task <- result.try(find_task(services.tasks, task_id))
  use Nil <- result.try(check_position(services.tasks, new_position))
  let other_tasks =
    list.filter(services.tasks, fn(other) { other.id != task_id })
  // Shift the other tasks to make room
  let #(before, after) = list.split(other_tasks, new_position - 1)
  Ok(list.flatten([before, [task], after]))
}
```

### Using in a Controller

The controller becomes a simple coordinator:

#### The reorder controller <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_tasks.gleam#L42-L58"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn reorder(
  request: Request,
  _context: EmptyContext,
  services: Services,
) -> Response {
  let result = {
    use id <- result.try(require_int(request, "id"))
    use form <- result.try(require_form(request))
    use new_position <- result.try(require_field_int(form, "position"))
    reorder_task(services, id, new_position)
  }

  case result {
    Ok(tasks) -> json_response(ok, task_ids_to_json(tasks))
    Error(failure) -> respond_with_error(failure)
  }
}
```

This controller uses `require_int` to safely extract the path parameter
and `require_field_int` to read `position` from the form body, then
calls the operation. The `use` syntax keeps the code flat and
readable.

All errors from the parameters and from the operation (which returns
`Result(_, Error)`) flow into the final `case result`.
`respond_with_error` turns each one into an HTTP response with
`error.to_status_code` and `error.message`.

The important shift is:

- Before: controller both **decides** what to do and **does** it.
- After: controller **decides** what to do, Operation **does** it.

### Benefits

1.  **Testability:** You can unit test the operation without mocking HTTP requests.
2.  **Reusability:** Call the same operation from a REST API, a GraphQL resolver, or a background job.
3.  **Clarity:** The controller reads like a summary of what's happening, not the implementation details.

### Advanced: Service Coordination

Operations are the perfect place to coordinate multiple services.

#### The publish_post operation <a href="https://github.com/TrustBound/dream/blob/3.0.0/test/snippets/operations_guide_posts.gleam#L21-L31"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```gleam
pub fn publish_post(services: Services, post_id: Int) -> Result(Post, Error) {
  use post <- result.try(find_post(services.posts, post_id))
  let published_post = Post(..post, published: True)

  // Side effects coordinated here. A failure stops the chain and comes
  // back to the controller as an Error.
  use Nil <- result.try(services.add_to_search_index(published_post))
  use Nil <- result.try(services.notify_subscribers(published_post))

  Ok(published_post)
}
```

Use the `use` syntax (Gleam's equivalent of `do` notation) to chain operations flatly, avoiding nested cases.

Do not discard the result of a side effect with `let _ =`. If the search index or the mailer fails, nobody then sees the error. In the example, each side effect returns a `Result`, and a failure comes back to the controller.

**Important:** Operations should return `Result(_, Error)` to keep error handling consistent across the application. This allows controllers to handle all errors uniformly without needing to map between different error types.

## Models with more hints

Models handle data access. They are functions that:

1.  Take a database connection.
2.  Run one SQL query each.
3.  Return domain types and data errors (`dream_errors.Error(client.QueryError)`).

dream_model generates all three parts. These examples come from the
project model in the tasks example. Each `.sql` file of
`src/models/project/` becomes one function of `src/models/project.gleam`.

#### Getting a Single Record <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/get.sql"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```sql
-- returns: one Project
SELECT
  id,
  name,
  description,
  color,
  created_at
FROM projects
WHERE id = $1;
```

`returns: one Project` gives `get(db, id) -> Result(Project, Error)`.
With no row, it returns `NotFound("Project not found")`, which answers

#### Listing Multiple Records <a href="https://github.com/TrustBound/dream/blob/3.0.0/examples/tasks/src/models/project/list.sql"><img align="right" alt="Tested snippet" src="https://img.shields.io/badge/%F0%9F%A7%AA_tested-snippet-lightgreen.svg?style=flat-square"></a>

```sql
  created_at
```

`returns: many Project` gives `list(db) -> Result(List(Project), Error)`.

### Best Practices

- **Do Not Edit Generated Code:** Change the `.sql` file and run
  `make models`. Keep input rules in an operation.
- **Explicit Connection:** Pass `db: Connection` explicitly.
- **Name the Unique Constraints:** Use `-- unique: <constraint>` for
  each unique constraint that a user can break. A violation of it gives
  `dream_errors.Conflict`, and `client.violated_constraint` reads the
  name of the constraint from its cause.
- **Texts in the Operations:** The generated functions return data
  errors, with no HTTP status and no text for the client. Map them in
  the operation: give a missing row and a taken unique value their own
  texts, and send every other error through `error.from_shared`, so the
  controllers handle one error type, `dream.Error`.
- **Check the Schema:** Give the `schema_fingerprint` of each model to
  `client.check_schema` at start-up.

## Common pitfalls

- **A generated model is out of date.** dream_model generates each model from its `.sql` files and the live schema. After you change a query or a migration, run `make migrate` and then `make models`. The app stops at start-up when the schema changed after the generation, and the example's integration run fails when a model isn't what `gleam run -m dream_model -- --check` expects.
- **The app stops at start with a database error.** The schema check runs a query at start-up, so the app needs the database. When the pool has no connection, the app prints one line for each attempt, such as `Waiting for the database (6s of 30s): The schema fingerprint query of models/user failed: ConnectionUnavailable`, and runs the check again 2 seconds later. It stops trying 30 seconds after the first check. So a database that starts at the same time as the app, for example in Docker Compose, does not stop the app. When the database is still down after 30 seconds, the app prints one message and stops with exit status 1. A changed schema, or another database error such as a missing table, stops the app at once, with no wait. Start PostgreSQL first, or run `make migrate` and `make models` after a schema change. In production, let your supervisor or orchestrator restart the app, and keep the health check.
- **One type, other columns.** Every query that returns one type must give the same columns, in the same order, with the same types. Otherwise dream_model stops with the first difference. A query with other columns, such as a count, needs another `returns:` hint, for example `-- returns: one` for one column.
- **A side effect's result thrown away.** `let _ = search.index(post)` hides a failure. Return a `Result` from every step of an operation and chain them with `use`.
- **Port 5432 is taken.** The example maps PostgreSQL to port 5435 on your machine, so it doesn't collide with a local PostgreSQL.
